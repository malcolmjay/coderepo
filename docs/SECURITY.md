# Security model

## Identity and customer access

Firebase Authentication generates and sends single-use email sign-in links. Its browser SDK verifies the link and the receiving email. The portal never implements its own passwords, codes, email outbox, or SMTP sender. Email addresses are not put in redirect query parameters. The callback token is removed from browser history before continuing. Sessions use Firebase's session persistence in the browser; tokens are available to JavaScript, so the app escapes content and serves a strict CSP with no inline scripts or third-party analytics.

A Firebase Auth identity is **not** a customer entitlement. Unknown addresses can verify identity but cannot access the portal data or files. Every callable operation requires a verified email, an active `members/{normalizedEmail}` document, and a sign-in time at or after that member's `validAfter`. The database role controls admin operations; a role or publication flag supplied by a client does not grant permission. Email normalization trims and lowercases but does not collapse plus aliases or Gmail dots. This implementation excludes slash-containing email local parts because emails are used as document IDs.

Revoke/restore operations update a server-owned validity cutoff. An old token stays unusable after restoration, even when Firebase refreshes that token, because its `auth_time` remains the original sign-in time. The cutoff is rounded into the following second; wait a moment before requesting a new link immediately after a change. Authorization is checked again inside transactions for administrative mutations. A request that already passed authorization may complete during revocation.

Firestore rules deny all browser reads and writes. Only the callable Function and trusted Google Cloud operators use the Admin SDK, which bypasses rules. The Function therefore checks membership on every route. Customers cannot browse the allowlist, see audit records, set their role, edit releases, or read drafts. Administrator changes require the trusted CLI script; the website cannot promote administrators.

## Uploads and downloads

Uploads go from the administrator's browser directly to the Firebase Storage API using Firebase's resumable upload SDK. They are not buffered through a Function. Storage rules check the administrator's verified identity, current membership, validity cutoff, upload owner, pending release, exact declared size, and binary MIME type. Only creation is allowed; overwrites, metadata edits, deletions, and reads through the client Storage API are denied, including for administrators. The browser and backend share a 20 GiB maximum file size; Storage rules enforce the same 21,474,836,480-byte limit. The SDK reads the selected File in resumable chunks rather than buffering an image in browser memory. Uploads can be paused and resumed while the page stays open, and temporary network failures can retry for up to 30 minutes. Page closure requires a new upload and can leave a draft; admins can verify completed uploads or remove unfinished drafts.

The trusted completion operation checks the staging object's size/type/generation, copies that exact generation into a private `releases/` object with fresh metadata excluding `firebaseStorageDownloadTokens`, sets attachment disposition, verifies the final object, and deletes the staging object before marking the draft ready. This prevents accidental distribution of permanent Firebase bearer URLs. Copies stay inside Cloud Storage, and the Function does not buffer file bytes. The Function has a five-minute timeout, and the browser allows six minutes for completion verification. These are verification deadlines, not limits on upload duration. The client can only create `uploads/` objects; all client operations on `releases/` are denied. The application never calls `getDownloadURL`. Unverified files cannot be published. Publishing metadata and files are separate explicit steps.

The download operation checks active membership and publication each time, requires explicit acceptance of the current download license, and records that acceptance before issuing a V4 Cloud Storage URL lasting 60 seconds and pinned to the verified generation. Files use an inert binary content type, attachment disposition, and `private, no-store` caching. Uploading another version creates a different path. Browser-supplied paths, generations, roles, sizes on edits, and extra publication fields are ignored.

The personal-use license is defined once in `functions/src/download-license.ts` and shared by the browser and server. Customers and administrators must check the agreement box on each visit to a file-list page; acceptance is not remembered across reloads or navigation. Every download request requires `licenseAccepted: true` and the exact current `licenseVersion`; missing, false, truthy substitutes, and outdated versions are rejected. The private activity record includes the authenticated email and UID, release ID, server timestamp, license version, exact displayed wording, and agreement label. Client-supplied identity, time, and legal text are ignored. A failed audit write prevents issuing a link. A consent record is evidence of the request's explicit acceptance, not proof that a person read the text or that the file transfer completed. It can exist even if the later IAM signing step fails. Change the version whenever the license wording changes, and deploy both Functions and Hosting.

Signed URLs are bearer credentials until expiry. A user can share a URL during that short window, a transfer started before expiry can continue, and a file already downloaded cannot be recalled. Revocation and unpublication block future authorization; they cannot erase existing copies or instantly invalidate an already issued URL. Administrators can intentionally share their own source files; the portal is access control, not DRM.

## Hosting and operations

Firebase Hosting serves HTTPS and security headers including CSP, no-referrer, anti-framing, and MIME-sniffing protection. The client uses bearer tokens for callable requests; there is no cookie-based custom action endpoint requiring a separate CSRF token. Firebase callable validation verifies ID tokens, and application authorization checks the allowlist. No cloud private keys or admin credentials are bundled into the browser.

The Function and Firestore deployment configuration use Montréal (`northamerica-northeast1`). Select the same region when creating the Storage bucket. Firebase Hosting uses a global CDN, and [Firebase Authentication processes data in the United States](https://firebase.google.com/support/privacy#data_storage_and_processing_locations); choosing Montréal for these regional resources does not guarantee Canada-only processing across Firebase. Firebase's built-in Auth email sending uses project quotas and abuse controls. App Check is not enforced in this starter; unauthenticated callers can still attempt Auth operations and consume some platform quota even though they cannot access files. Monitor usage and consider App Check/rate controls if traffic warrants them. A max-instance setting and billing alerts are not a hard cost ceiling.

Protect the Google/Firebase operator account and administrator mailbox with MFA. Keep the bucket private with public access prevention. IAM signing permissions must be restricted to the runtime identity. Follow the live deployment smoke check before launch. There is no automatic commerce synchronization, per-product entitlement system, malware scanner, firmware signing service, or independently calculated SHA-256 in this version. Checksums are publisher supplied; verify original release files before publication.

## Verification and recovery

Emulator tests exercise real email-link authentication, callable authorization, Firestore denial, Storage cross-service rules, draft visibility, exact-size uploads, immutability, removal of permanent download tokens, revocation, and publication. Production signed URL signing and email delivery are separate live checks. The local demo deliberately does not provide a production-shaped download bypass.

Activity records capture administrator changes and accepted download-license requests, but never signed URLs, auth tokens, or login links. Download completion is not tracked. Retain independent original release files and configure database and storage recovery as needed. Draft deletion is destructive after the admin confirms it; downloads already in progress follow Cloud Storage behavior. Secret-bearing `.env` files and service-account credential files are excluded from git.
